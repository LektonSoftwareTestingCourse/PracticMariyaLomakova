# Тестовый план СМП

## 1. Область тестирования и подход

План охватывает всю СМП. Authorization и Card-Management проверяются глубоко как ядро: для них подготовлены классы эквивалентности, тройки граничных значений, PICT-модели и воспроизводимые тест-кейсы. Остальные сервисы проверяются по дымовому и критическому чек-листам. Подход спецификационный, по принципу чёрного ящика, риск-ориентированный

Порядок выполнения: готовность окружения → smoke всей системы → тесты ядра P0 → интеграционный критический путь → проверки периферии P1/P2 → повторный прогон затронутых проверок после изменений.

## 2. Критерии входа

Тестирование начинается, когда одновременно выполнены условия:

- требования `tz/04-authorization.md`, `tz/05-card-management.md`, архитектура и API-контракты доступны и приняты как тестовый базис
- Docker Compose запускает все сервисы, PostgreSQL и RabbitMQ; обязательные health-check возвращают успешный статус
- Gateway доступен на порту 8080, Dashboard — на 3000, RabbitMQ Management UI — на 15672
- сгенерировано не менее 20 тестовых карт по известным BIN, среди них доступны карты для подготовки требуемых статусов, лимитов и балансов
- PICT установлен, обе модели проходят разбор, оба набора сгенерированы и содержат строки данных
- тестовые данные изолированы от чужих прогонов либо состояние БД перед кейсом известно и воспроизводимо

## 3. Критерии выхода

Работа считается завершённой, когда одновременно достигнуты измеримые условия:

- 100% обязательных компонентов артефакта присутствуют по путям из задания
- 100% выделенных классов эквивалентности и троек граничных значений ядра связаны хотя бы с одним тест-кейсом
- 26 строк Authorization и 22 строки Card-Management из PICT-наборов спроецированы в отдельные тест-кейсы
- выполнены 100% пунктов дымового и критического чек-листов либо для невыполненного пункта зафиксирована причина блокировки
- пройдены 100% проверок P0 и не менее 95% всех запланированных проверок
- отсутствуют открытые дефекты критического и высокого уровней, препятствующие денежной целостности, маршрутизации или логированию
- результаты повторяемы на чистом запуске окружения, а лёгкий CI ветки завершён успешно

## 4. Критерии приостановки и возобновления

### 4.1. Приостановка

Проверки приостанавливаются, если не запускается Gateway либо один из сервисов ядра, недоступны PostgreSQL/RabbitMQ, невозможно создать управляемые тестовые данные, ответы API массово не соответствуют контракту или обнаружено нарушение денежной целостности, из-за которого последующие результаты недостоверны.

### 4.2. Возобновление

Проверки возобновляются после устранения блокирующей причины, успешного health-check затронутых компонентов, восстановления известного состояния данных и повторного прохождения соответствующего smoke-набора. После исправления дефекта сначала повторяется его тест-кейс, затем связанные P0/P1-проверки.

## 7. Риски

| Риск | Влияние | Снижение риска |
|---|---|---|
| Расхождение ТЗ, OpenAPI и реализации | Неоднозначный ожидаемый результат | Тестовый базис фиксируется ссылкой на требование; неоднозначности не подменяются предположениями |
| Случайность данных симуляторов и генератора карт | Невоспроизводимые проверки | Для ядра используются конкретные подготовленные данные; случайные значения не включаются как управляемые pairwise-факторы |
| Остаточное состояние лимитов и баланса | Ложные отказы последующих кейсов | Отдельные карты/фикстуры и восстановление исходного состояния перед кейсом |
| Асинхронная доставка через RabbitMQ | Проверка выполняется раньше обработки события | Ограниченное ожидание и проверка конечного состояния в Logger/Notification Service |
| Неатомарность проверки и резервирования | Race condition при параллельных операциях | В функциональном наборе последовательный запуск; конкурентный риск фиксируется для отдельного нагрузочного тестирования |
| Изменение модели PICT | Устаревшее соответствие строк тест-кейсам | После изменения модели набор полностью перегенерируется, нумерация и маппинг проверяются повторно |

## 8. Метрики

- доля требований ядра, связанных с тестовыми условиями и тест-кейсами;
- доля покрытых классов эквивалентности и границ;
- доля строк PICT, спроецированных в отдельные тест-кейсы — целевое значение 100%;
- количество выполненных, пройденных, непройденных и заблокированных тестов;
- процент прохождения P0/P1/P2-проверок;
- число открытых дефектов по критичности;
- доля выполненных пунктов smoke и critical-path чек-листов;
- стабильность повторного прогона: число тестов с отличающимся результатом без изменения системы.
