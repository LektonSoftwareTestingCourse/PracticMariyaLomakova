### Сводная таблица

Математика для `api / integration` в итоге такая: 

старые 19 API и 50 integration \+ новые 4 API и 3 integration = итого 23 API и 53 integration.

Получилось 37,6% unit, 60,8% API/integration и 1,6% E2E. Распределение не совпадает с ориентиром 70/20/10, потому что исходный тест-дизайн практики 2 подробно проверяет REST-контракты Card Management, пагинацию, фильтры, soft delete и резервирование с состоянием PostgreSQL, и эти проверки нельзя адекватно перенести в unit без потери основного риска.

Вообще в микросервисной СМП доля API/integration выше 20% из-за плотных HTTP-контрактов, общей PostgreSQL, блокировок при резервировании, RabbitMQ, outbox и eventual consistency. Основные дефекты вероятны именно на границах сервисов и инфраструктуры.

E2E тут всего два: один базовый happy path из практики 2 и один критичный сценарий publisher failure –> reversal, а остальные правила дешевле и точнее проверяются на unit, API или integration. 

Риска ice-cream cone по E2E нет: их только 1,6%. При этом есть смещение в integration, но оно объясняется большим числом DB-ориентированных кейсов Card Management. Дефицита контрактных проверок тоже нет: 23 API-кейса проверяют HTTP-валидацию отдельно от 53 интеграционных проверок.
